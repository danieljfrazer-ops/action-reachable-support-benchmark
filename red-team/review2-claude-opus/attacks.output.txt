        at ARL_0 = 1000 steps that single run contains ~   2,560 EXPECTED FALSE ALARMS
    confirmation-design.csv has 1764 rows; at 1 mask/run that is 1,128,960,000 environment steps of simulation.
    HONEST CORRECTION (see throughput.py, measured on this arm64 host at 168,190 bare SCM
    steps/s): 1.13e9 bare SCM steps is only ~1.9 h, so raw stepping is NOT the binding
    constraint and a 'too slow' claim here would be wrong. The binding problem is STATISTICAL:
      * a run long enough for one published-configuration IBD mask contains ~640 expected
        false alarms at ARL_0 = 1000 steps, against ~1 change event. No one operates a change
        detector at that point; the HPDT event-matching machinery (p=3, r=20, w_T=50) is
        swamped -- P(a false alarm lands inside w_T=50 of the event) ~ 50/1000 = 5% per event,
        which is spurious 'detection' at zero delay for BOTH arms.
      * either ARL_0 must scale with the run length (e.g. a fixed false-alarm probability over
        the run), or the run must be short and sequential IBD must run at a probe configuration
        far below the published one -- at which point 'IBD as published, reproduced to numerical
        anchors' (contract H) no longer describes the confirmatory arm.
    confirmation-design.csv declares no steps_per_run and no events_per_run column, so this
    trade-off is currently invisible in the frozen run matrix.

      LB(Delta) > 20 on scm_L and scm_N; LB(I) > 0 on scm_L and scm_N; sign on cartpole and pendulum.

      if each condition independently had power 0.80, joint power = 0.262

    difference in miss rate at zero delay difference: the 'detection delay' framing is not
    what the primary estimand measures.
